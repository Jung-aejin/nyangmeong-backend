# 구현 검증

구현한 대화를 보지 않고 저장소만 보고 판정한다. 보고는 처음부터 끝까지 한국어로 쓴다. 파일을 고치지 않고 고칠 곳은 보고만 한다(검증 루프 잠금은 `scripts/verify-loop.sh`로만 남긴다). 변경은 diff로 확인하고 추측하지 않는다.

1. `handoff/<이름>.md`(`<이름>`은 브랜치 이름)의 "지금 하는 것"에서 기획과 시작 시각을 읽는다. 기획이 없으면 "기획 없음"이라고 하고 멈춘다.
2. 바뀐 것: `git status -sb`, `git diff HEAD --stat`, `git log --since="<시작 시각>" --stat`.
3. AGENTS.md의 검증 명령을 하나씩 돌려 종료 코드를 적는다.
4. 기획과 대조한다.
   - 기능 ID마다 구현한 변경이 있는가.
   - 기획에 없는 파일이 바뀌었는가. `handoff/`·`milestones/`, 기획한 클래스를 받치는 보조 파일(설정 값 클래스 등)과 그 테스트는 세지 않고 비고에만 적는다.
   - `package.json`·`build.gradle`에 `새 의존성:`에 없는 라이브러리가 들어왔으면 기획 밖 변경이다.
   - `sh scripts/verify-loop.sh check`가 파일을 출력하면 첫 실패 뒤 기준 파일(기획·검증 명령·의존성·테스트)이 바뀐 것이다. `기준 변경:`에 적는다.
5. `화면:` 완료 조건은 AGENTS.md의 방법으로 확인한다. 못 하면 이유를 적는다.
6. 판정이 `실패`면 `sh scripts/verify-loop.sh fail "<실패 항목 한 줄>"`을 돌려 나온 회차를 적는다. 아니면 `sh scripts/verify-loop.sh clear`.
7. 보고한다.

```
검증 명령: <명령> → <종료 코드> (실패 줄)
기획 밖 변경: <파일> 또는 없음
기준 변경: <파일> 또는 없음
| 기능 ID | 변경 있음 | 명령 | 화면 | 비고 |
판정: 통과 / 실패 / 확인 못 함 있음
회차: <verify-loop.sh 출력> (실패일 때만)

사람 확인:
- 띄우기: <명령>(어느 저장소에서)
- <기능 ID>: <전체 URL 또는 API 메서드·경로> → <할 동작·넣을 값> → <기대 결과>
- 테스트로만 확인할 것: <조건> → `<테스트 명령>`
- 정리: <확인용 데이터 지우는 방법> 또는 없음
- 바뀐 파일: <목록>
```

- 판정은 하나만 고른다. 검증 명령이 0이 아니거나, 변경 없는 기능 ID가 있거나, 기획 밖 변경이나 기준 변경이 있으면 `실패`. 그렇지 않고 확인 못 한 완료 조건이 있으면 `확인 못 함 있음`. 둘 다 아니면 `통과`.
- "사람 확인"은 판정과 관계없이, 사람이 그대로 따라 할 수 있게 쓴다. 기능 ID는 기획에 적힌 짝을 그대로 쓴다. 값은 코드에서 확인한 실제 값이다(README "사람 확인" 참고).
  - 프론트: `routes/paths.js`로 만든 전체 URL(`http://localhost:5173/...`), 누를 요소.
  - 백엔드: `http://localhost:8080/swagger-ui.html`에서 찾을 API, 넣을 값, 기대 응답. 로그인이 필요하면 그 조건의 테스트와 `./gradlew test --tests '<클래스>'`. 상태를 바꾸는 요청은 `X-Requested-With: XMLHttpRequest`를 넣은 `curl`도.
- 마지막 줄:
  - 통과: "위 '사람 확인'대로 확인한 뒤 `/done`으로 마무리하세요"
  - 실패: "고칠 곳을 고친 뒤 `/verify`를 다시 실행하세요"
  - 확인 못 함 있음: "확인할 수 있게 되면 `/verify`를 다시 실행하세요. 지금 멈추려면 `/done`(마일스톤은 끝나지 않습니다)"
