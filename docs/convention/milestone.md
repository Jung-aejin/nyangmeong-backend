# 마일스톤 만들기

내 담당 화면·API를 마일스톤으로 나눌 때 연다. 처음 한 번 만들고, 명세가 바뀌면 다시 만든다. 프론트 저장소와 백엔드 저장소에 같은 문서가 있다. 고칠 때 둘 다 고친다.

마일스톤 하나 = 화면 ID 하나. 담당자가 자기 몫의 프론트와 백엔드를 둘 다 구현한다. 마일스톤 파일은 저장소마다 따로 두고, 프론트 저장소에는 "화면" 담당 몫을, 백엔드 저장소에는 "API" 담당 몫을 적는다. 마일스톤은 번호 없이 화면 ID로 부른다. 화면 ID는 명세에 정해진 값이라 두 저장소에서 같다.

## 절차

1. 이니셜은 브랜치 이름이다(`/`가 있으면 앞부분). 아래 "담당" 표에서 내 줄을 찾는다. 없으면 멈추고 사람에게 묻는다.
2. DMS MCP의 `search_documents`로 내 도메인의 기능명세서를 찾는다(예: `공통레이아웃_기능명세서`). 같은 도메인 문서가 여럿이면 파일명 날짜가 가장 늦은 것을 쓴다.
3. `read_document`로 "기능 목록" 시트만 본다. 화면 ID 칸은 병합 셀이라 첫 행에만 값이 있다. 비어 있으면 위 행과 같은 화면이다.
4. 화면 ID별로 기능 ID와 기능명만 옮긴다. 기능 설명은 옮기지 않는다. 구현할 때 그 화면 것만 다시 읽는다.
5. "화면과 API 담당이 다른 곳" 표를 적용한다. 명세가 누구 것이든 표에서 화면이 내 것이면 프론트 마일스톤에, API가 내 것이면 백엔드 마일스톤에 넣는다. 내 명세에 있어도 화면이 남의 것이면 프론트 마일스톤에서 빼서 "제외"에 적고, API가 남의 것이면 "API가 남의 것"에 적는다.
   - 백엔드는 같은 API나 같은 서버 동작을 쓰는 기능 ID를 처음 나오는 화면의 마일스톤 하나에 모은다(예: 세션 만료 FN-COM-002-24·003-07, 회원 요약 조회 FN-COM-002-15·005-02). 다른 화면의 기능 ID에는 "(화면은 SCR-…)"을 붙인다. 같은 서버 동작이 두 마일스톤에 나뉘지 않게 한다.
   - 화면 ID가 없는 공통 기반(`global/` 등)은 그것을 처음 쓰는 화면의 마일스톤에 "함께 만드는 것"으로 적는다.
6. "먼저 나와야 하는 것" 표에서 내가 기다리는 것을 마일스톤마다 적는다. 순서는 남이 기다리는 내 것이 든 마일스톤을 앞에, 그다음 기다리는 것이 적은 마일스톤을 앞에 둔다. 기다리는 것이 있어도 마일스톤을 뒤로 미루기만 하고 빼지 않는다.
7. 마일스톤마다 완료 조건 후보를 1~2개 적는다(예: "목록 API가 200과 빈 배열을 돌려준다", "헤더가 로그인 여부에 따라 바뀐다").
8. 읽은 기능명세서마다 "기능 목록" 시트의 기능 ID 수를 센다. 그 수는 마일스톤에 넣은 기능 ID 수와 "제외" 절에 적은 기능 ID 수를 더한 값과 같아야 한다. 다르면 빠진 기능 ID를 찾아 마일스톤이나 "제외"에 넣는다. 제외에는 이유(누구 담당인지와 근거)를 적고, 보고할 때 제외한 기능 ID를 빠짐없이 나열한다. 이유가 다른 기능 ID를 한 범위(`005-06~08`)로 묶지 않는다. 담당이 다른 기능 ID만 따로 적고 그 담당을 붙인다(예: "005-07 로그아웃 처리는 AIC, 나머지는 화면만 있다").
   개수가 맞으면 내용을 확인한다: 같은 서버 동작이 두 마일스톤에 있지 않은가, 기능 ID가 그 마일스톤의 화면 ID 소속인가(아니면 "(화면은 SCR-…)"이 붙었는가), 제외 이유가 기능 설명과 맞는가.
9. `milestones/<이니셜>.md`에 아래 형식으로 쓴다. 공개 저장소이므로 비밀값과 개인 PC 경로를 쓰지 않는다. 커밋은 사람이 정한다.
10. `/start`가 부른 경우에는 멈추지 않고 `/start`의 다음 단계(마일스톤 고르기·기획)로 이어 간다. 따로 요청받아 만들었으면 보고 마지막 줄에 "`/clear` 한 뒤 `/start`로 첫 마일스톤을 시작하세요"라고 적는다.

화면설계서와 요구사항정의서는 이 단계에서 읽지 않는다(화면설계서는 한 파일이 수백 KB다). 마일스톤 하나를 구현할 때 그 화면 ID 부분만 찾아 읽는다.

```
# <이니셜> 마일스톤

기준: <기능명세서 파일명> (DMS, <확인한 날짜>)

## SCR-COM-002 헤더 — 대기
- 기능: FN-COM-002-01 로고 이동, FN-COM-002-02 …
- API가 남의 것: FN-COM-004-02~12 (YAY)
- 함께 만드는 것: (공통 기반이 있을 때만) `global/response` …
- 기다리는 것: member 로그인·회원 조회 (AIC)
- 완료 조건: …

## 제외
- FN-XXX-000-01~05: 화면 담당이 다른 사람(그 이니셜과 근거 화면 ID)

## 대조
- 공통레이아웃: 명세 117 = 마일스톤 117 + 제외 0
```

상태는 `대기`·`진행`·`끝` 중 하나다. `끝`은 `/done`만 정한다(기준은 `.claude/skills/done/SKILL.md` 5번). 남의 API·화면을 기다려 연결만 남은 기능은 `끝`을 막지 않고 그 절의 `연결 남음:`에 남는다. 다음 작업은 `대기` 중 맨 위의 것을 고른다. "기다리는 것"은 순서를 정하는 참고일 뿐 막는 조건이 아니다. 아직 나오지 않은 남의 API는 가짜 응답으로 먼저 만들고 나중에 연결한다.
