# 구현 검증

이 검증은 구현한 대화를 보지 않고 저장소만 보고 판정한다. 파일을 고치지 않는다. 고칠 곳은 보고만 한다.

1. `<이름>`은 `git branch --show-current`의 브랜치 이름이다(`/`가 있으면 앞부분). `handoff/<이름>.md`의 "지금 하는 것"에서 기획(기능 ID별 바꿀 파일, 부를 API, 완료 조건)과 시작 시각을 읽는다. 기획이 없으면 "기획 없음"이라고 보고하고 멈춘다.
2. 바뀐 것을 모은다: `git status -sb`, `git diff HEAD --stat`, 시작 시각 이후 커밋(`git log --since="<시작 시각>" --stat`).
3. AGENTS.md의 검증 명령을 하나씩 돌리고 종료 코드를 적는다. 실패하면 실패한 줄만 옮긴다.
4. 기획과 대조한다: 기획에 없는 파일이 바뀌었는가, 기획의 기능 ID마다 그것을 구현한 변경이 있는가. 변경은 diff로 확인하고 추측하지 않는다. `handoff/`와 `milestones/`는 `/start`·`/done`이 고치는 파일이라 기획 밖 변경으로 세지 않는다. `package.json`·`build.gradle`에 추가된 라이브러리가 기획의 `새 의존성:`에 없으면 기획 밖 변경으로 센다.
5. `화면:` 완료 조건이 있으면 AGENTS.md에 적힌 방법으로 확인한다. 확인하지 못한 조건은 이유를 적는다(예: API 없음).
6. 보고 형식:

```
검증 명령: <명령> → <종료 코드> (실패 줄)
기획 밖 변경: <파일> 또는 없음
| 기능 ID | 변경 있음 | 명령 | 화면 | 비고 |
판정: 통과 / 실패 / 확인 못 함 있음

사람 확인:
- 띄우기: <명령> (README "사람 확인")
- <기능 ID>: <브라우저에 붙여 넣을 전체 URL 또는 API(메서드·경로)> → <할 동작·넣을 값> → <기대 결과(화면 모습, 응답 코드·JSON)>
- 테스트로만 확인할 것: <조건> → `<테스트 실행 명령>`
- 정리: <확인하려고 만든 데이터를 지우는 방법> 또는 없음
- 바뀐 파일: <파일 목록>
```

판정은 검증 명령이 모두 0이고, 모든 기능 ID에 변경이 있고, 기획 밖 변경이 없을 때만 `통과`다.

"사람 확인"은 판정과 관계없이 쓴다. README의 "사람 확인" 절을 읽고 그 방법에 맞춰, 사람이 그대로 따라 할 수 있게 기능 ID마다 한 줄 이상 쓴다. 주소·경로·값은 코드에서 확인한 실제 값을 쓰고 추측하지 않는다.
- 프론트: 실제 라우트(`routes/paths.js`)로 만든 전체 URL(`http://localhost:5173/...`)과 누를 요소(버튼 글자 등)를 적는다.
- 백엔드: `http://localhost:8080/swagger-ui.html`과 Swagger에서 찾을 API(메서드·경로·`@Operation` 요약), 넣을 요청 값, 기대 응답을 적는다. 로그인이 필요해 Swagger로 부를 수 없으면 그 조건을 검증하는 테스트 클래스와 `./gradlew test --tests '<클래스>'`를 적는다. 상태를 바꾸는 요청은 `X-Requested-With: XMLHttpRequest` 헤더를 넣은 `curl` 명령도 적는다.

7. 보고 마지막 줄에 판정에 맞는 다음 단계를 적는다.
   - 통과: "위 '사람 확인'대로 직접 확인한 뒤 `/done`으로 마무리하세요"
   - 실패: "위 고칠 곳을 고친 뒤 `/verify`를 다시 실행하세요"
   - 확인 못 함 있음: "확인 못 한 조건을 확인할 수 있게 되면 `/verify`를 다시 실행하세요. 지금 멈추려면 `/done`으로 남은 일을 핸드오프에 남기세요(마일스톤은 `끝`이 되지 않습니다)"
